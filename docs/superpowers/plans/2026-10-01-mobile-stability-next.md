# 移动端录音稳定性：FFT 实验后的优化计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking. 先执行测量与基频去重实验；后续条件阶段须根据新数据收敛设计，不把本路线图当作 Worker 的完整实现规范。

**Goal:** 优先降低真机录音中的随机停顿，允许图表降低更新频率，同时保持音频分析正确性和输入连续性。

**Architecture:** 以已验证的频谱 FFT 候选作为下一轮基线，每次只验证一个改动。先补齐有声与热机测量，再消除重复基频计算；倒谱 FFT、显示调度及线程隔离按新热点依次决定，避免叠加未经验证的改造。

**Tech Stack:** TypeScript、React、Zustand、ECharts、Web Audio、Vitest；Android Chrome USB 远程测量。

**Spec:** 本轮用户要求“规划下一步的优化方向”；已确认约束为稳定优先、覆盖中低端机型。证据参见 ../../performance/fft-experiment.md；这是后续实验路线，不是新功能的完整设计批准。

## 已确认和待确认

已确认：安静录音三组 P95 从215.9–232.5ms降至49.8–66.4ms；每15秒>100ms间隔从87–95次降为0，但仍有34–49个长任务，占用1.895–2.974秒。这个结果支持频谱FFT改动，却没有确定剩余长任务的来源。

源码候选：同一有声帧 detectPitch 被 pipeline 和 LPC/倒谱重复调用，hybrid回退最多三次；倒谱仍走旧 Complex FFT，正/逆/正三次2048点变换；LPC求根与UI提交也可能造成尾部延迟。它们的最新实际成本占比尚未测量。

已有400点独立FFT微基准不是生产800点输入。真实录音A/B是生产链路测量，但需用800点补齐微基准，不能把400点吞吐直接套入整体录音。

## 检查重点

1. voiced但F0为null时去重必须保留null，不能误用空值合并又重算。
2. hybrid触发倒谱回退时，基频、共振峰与谐波过滤保持原结果。
3. 连续录音填满历史窗口并升温后，尾延迟、内存及反馈延迟不随时间增长。
4. 停止、清空、重新录音、后台恢复后，旧结果不得覆盖新会话；Worker阶段尤其需要验证。
5. 图表降频或抽稀必须保留断点和短峰，反馈不能通过展示过期分析结果制造“流畅”。

## 阶段5：线程隔离（满足条件才进入）

**涉及边界：** AudioEngine采集、AnalysisPipeline计算、useAnalysis会话生命周期、recordingBuffer音频所有权及显示/存储发布。

若DSP降低成本后仍频繁占用主线程超过约20ms/批，或trace确认它阻塞交互，先设计Worker协议，再实现独立线程实验。Worker不能降低总计算需求；应同时确认平均计算吞吐足以跟上音频流。

需要设计：会话ID/递增序号、停止与flush、清空/重新录音隔离、缓冲所有权、队列上限、结果合批、故障恢复。队列不能无限积压，也不能任意丢PCM使检测时间轴和算法状态失真。AudioWorklet仅在实测采集回调丢失/迟到后单独考虑，采集迁移和DSP线程迁移分开验收。

这一阶段属于架构设计，需要在获得新证据后制定具体方案和测试；当前不锁定消息结构或丢帧策略。

## 收敛与交付规则

- 稳定性优先：比较P95/P99、长停顿和反馈新鲜度；不以平均FPS或纯FFT基准作为验收结论。
- 低端Android至少补一台实际目标手机，K70E仅代表当前可用实机。
- 每项改变保存基线和三组交替数据；长测独立报告升温后结果，不用前三十秒替代。
- 实验达标后才整理独立PR。FFT改动与旧PR的组合收益分别报告，不合并性能归因。
- 当前推荐下一次执行范围为阶段4剩余尾部归因及局部option实验；阶段5由新测量触发，分次设计和实施。
