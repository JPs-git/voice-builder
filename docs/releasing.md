# 发布版本与撤回

发布基线为最近可达的 Git 标签。普通提交按 Conventional Commits 判断：不兼容变更为 major，feat 为 minor，fix 为 patch，其余默认不发布。同一批变更取最高级别。

## 尚未发布的完整撤回

标准 Git 撤回正文保留 `This reverts commit <完整40位SHA>.`。目标提交和撤回都在本次发布范围内时，自动抵消；撤回的撤回会恢复原提交参与判断。

该处理依赖提交元数据，不检查代码是否实际完全抵消。只允许对完整撤回使用自动抵消。部分撤回、解决冲突时保留了额外修改等情况，应在撤回提交中增加明确决策，退出自动抵消，并在 PR 中审核最终差异。

## 已发布或无法自动配对的撤回

不会默认当作 patch。合并前评估相对于上一发布版本的兼容性，并在最终 squash 提交正文单独添加一行，例如：

```
Release-Bump: patch
```

可用值：none、patch、minor、major。无用户可见变更可以选 none；兼容性修复通常选 patch；新增兼容功能选 minor；移除已承诺的公共接口等不兼容变更选 major。不能只凭 revert 类型决定版本。

每个提交最多一个决策，拼写错误或重复会停止发布。显式决策是该提交的发布贡献，不会压低本批其他 feat、fix 或 BREAKING CHANGE 的级别。

如果撤回已合并且缺少决策，自动发布会失败，并且不会输出 bump。无需重写 master 历史：在 GitHub Actions 的 Auto Release 中选择 Run workflow，分支选择 master，再为 revert_bump 选择经审核的级别。auto 保持自动判断；其他值仅用于本批无法配对且没有自身决策的撤回，不覆盖已写明的决策，不压低其他变更。若多个撤回需要不同处理，逐项评估后选其中最高级别，并在发布记录中解释。

## 版本标签不可变

已发布的版本和标签保持不变。即使版本选高，也不降号、不覆盖标签。回退线上部署可以重新部署已有构建；代码撤回发布则使用新的递增版本。

流程发现即将创建的标签已存在时会停止，需人工调查部分发布状态，不自动删除标签。

## 验证

`node --test scripts/release-bump.test.mjs` 覆盖抵消、恢复、跨发布撤回、显式决策和真实临时仓库中的命令行失败与恢复。
