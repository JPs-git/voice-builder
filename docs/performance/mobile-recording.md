# 移动端录音稳定性验证记录

## 本轮实现

分支 `fix/mobile-frame-rate`，基线 `90ac031`。保留原分析算法、16kHz 请求采样率、10ms 分析步长和 1000 帧窗口。

- 预设引用未改变时跳过持久化，录音数据不再写入 localStorage。
- 一次音频 chunk 的分析结果批量提交，保留所有分析帧。
- 三张图、竖屏反馈和钢琴高亮读取统一显示快照，独立于分析存储。默认目标 15fps，持续绘图超时或刷新迟到降到 10fps；稳定 30 秒后尝试恢复，恢复失败冷却 60 秒。
- 显示调度不补画过期状态；清空立即清除，停止和导入立即发布最终快照；后台暂停显示，恢复仅发布最新状态。
- 录音活动状态由采集生命周期明确传入，不能把分析阻塞后的迟到数据误判为空闲。5 秒窗口至少 5 个样本可触发降档，恢复需至少 20 个，防止严重卡顿因样本太少而无法降档。
- 实时数据更新仅提交曲线数据、时间范围和最新 F0 标记；坐标轴样式及目标配置仅在控制项/布局/回放光标变更时提交。相同尺寸的 resize 通知跳过。

## 已执行的验证与证据

1. 原始基线：49 个测试文件、366 个测试通过。
2. 针对性回归先失败再通过：实时录音存储写入、批量发布次数、窗口截断、停止时保留完整帧、静态图表配置不重复提交、resize 去重。
3. 虚拟时钟覆盖：突发合并、卡顿后无补画、后台/恢复/卸载、显示与分析解耦、降档/恢复/冷却，以及发生在 invalidate 之前的 300ms 分析停顿。
4. 同一桌面 Node 环境，`assets/aoe.wav` 重采样为 16kHz 后按 1024 点分块，未 flush：5.957375 秒、591 个分析帧，修改前 591 次存储调用；修改后 93 次状态通知、0 次存储调用。没有丢分析帧。
5. 修改后该音频第二遍预热运行，分析与提交合计：每批平均 3.30ms、P95 5.09ms、最大 8.03ms。存储用计数替身；不包含浏览器绘图、真实存储或设备限速。这些数字不能证明手机稳定帧率达标。
6. 独立代码审查发现的“录音停顿误判空闲”问题已修复并加入回归。

最终自动化验证（2026-09-29）：`npm test` 53 个测试文件、381 个测试通过；`npm run build` 通过；`npx tsc --noEmit` 通过。生产构建有现有的 >500kB chunk 提示，不代表运行时帧率失败。

## 如何在真机测量

使用生产构建：`npm run build`，通过支持麦克风权限的 HTTPS 或受信任本地来源访问。不能直接把普通 LAN HTTP 当作真机麦克风测试环境。

在页面 URL 的 query 加 `perf=1`（例如 `/?perf=1`）。诊断默认关闭，启用后控制台可读取：

```js
window.voiceBuilderMetrics.clear() // 每个采样场景前清空
window.voiceBuilderMetrics.snapshot()
```

每种指标最多保留最近 2048 个数值，不保存或上传音频。返回 count/P50/P95/P99/max；长测中必须按场景定期导出，因为它不是完整十分钟日志。单位为 ms，`sampleRate` 例外，单位为 Hz。

| 指标 | 含义 |
|---|---|
| captureInterval | 麦克风回调间隔，含主线程迟到 |
| sampleRate | 实际 AudioContext 采样率（启动时采样，清空后不会重新产生） |
| analysis | 每个 chunk 的同步 DSP 用时，不含状态发布 |
| publish | 每批结果提交分析存储所需时间 |
| chartUpdate | 单次 ECharts.setOption 同步耗时，不含浏览器最终合成 |
| displayInterval | 显示调度发布间隔，不等于屏幕最终呈现间隔 |

同时采集浏览器 Performance trace，观察主线程长任务、GC、绘制和录音回调。iOS 用 Safari 远程检查；Android 用目标浏览器远程检查。仅看 setOption 用时或平均 FPS 不足以归因。

冷机每轮静音 30 秒、发声/静音交替 60 秒、持续发声 30 秒，每设备运行三轮；随后连续录音 10 分钟，记录热机表现。分别测分析页（两张图）和音高页，覆盖目标切换、暂停继续、清空、横竖屏和后台恢复。基线与修改后使用相同设备、浏览器、音源和供电条件。

初始目标：15fps 档显示间隔 P95≤100ms、P99≤150ms；10fps 档 P95≤150ms、P99≤200ms。稳态 >200ms 停顿逐个归因；控制操作和后台段单列。绘图同步总成本 P95 目标≤20ms；需从 trace 汇总两图，不能把单图分位数相加。检查分析延迟、热降频与内存是否持续增长。

## 尚未验证／条件阶段

| 项目 | 状态与下一步 |
|---|---|
| 低端 Android / 中端 Android / 旧款 iPhone | 当前环境无连接真机；帧率、发热、长任务、内存均未实测 |
| Web Worker | 尚未引入；若真机分析批次 P95>20ms 或 trace 证明 DSP 主导停顿，执行计划任务 5，包含会话隔离、transfer 安全和有界积压 |
| DPR 上限 / 显示抽稀 | 尚未启用；分别做真机 A/B，并验证清晰度、断点和短峰后决定 |
| AudioWorklet / FFT 重写 / 消除重复音高计算 | 未改动；只有明确的采集或 DSP 热点证据才进入相应改造 |

这一轮降低的是确定的额外开销并建立稳定显示调度，不能宣称已经解决所有中低端手机的随机卡顿。同步 DSP 仍可能阻塞主线程，降到 10fps 也不保证其计算吞吐达标。
